# NSM-001 — TCP Service Exposure and Connection Behavior

## Description

Controlled TCP connection tests were performed from the Windows client to the Ubuntu server.

The target system was:

```text
192.168.0.162

The source system was:

192.168.0.136

The following destination ports were tested:

22
23
80
443
Evidence

The TCP conversation analysis identified communication involving:

192.168.0.136:58140 → 192.168.0.162:22
192.168.0.136:58141 → 192.168.0.162:23
192.168.0.136:58142 → 192.168.0.162:80
192.168.0.136:58153 → 192.168.0.162:443

TCP/22 produced a response from the Ubuntu server and was associated with SSH traffic.

Ports 23, 80, and 443 did not produce a successful TCP handshake in the captured test traffic.

Security Significance

The observation provides network-level visibility into which tested services successfully responded to connection attempts.

This is useful during security assessments because exposed services increase the number of network entry points that may require monitoring and protection.

The result is also consistent with the Linux hardening work performed in Project 1, where SSH was retained as the required remote-access service while unnecessary services were disabled.

Assessment

The capture provides evidence that TCP/22 was reachable during the test while the other tested ports did not establish successful connections.

The capture alone does not establish why the other ports did not respond.

NSM-002 — Repeated TCP SYN Retransmissions
Description

Repeated TCP SYN retransmissions were observed during controlled connection tests against the Ubuntu server.

The affected destination ports included:

23
80
443
Evidence

The following Wireshark display filter was used:

tcp.analysis.retransmission

Repeated SYN transmissions were observed from:

192.168.0.136

toward:

192.168.0.162

on the tested ports.

The SSH connection on TCP/22 produced a response, while the other tested connections showed repeated SYN transmissions without a corresponding successful handshake in the capture.

Security Significance

Repeated SYN retransmissions can occur when a destination does not respond, traffic is filtered, a service is unreachable, or network conditions prevent successful communication.

In security monitoring, repeated connection attempts can provide useful indicators for investigating network reconnaissance or connectivity problems.

However, retransmissions alone are not sufficient evidence of malicious activity.

Assessment

The observation is classified as a low-severity network-monitoring observation because it represents a controlled test performed within the laboratory.

No malicious activity is inferred from the retransmissions.

NSM-003 — DNS Resolution Activity
Description

DNS traffic was observed during the laboratory capture.

The DNS traffic included queries generated by hosts within the laboratory environment.

Observed DNS activity included domain resolution requests such as:

connectivity-check.ubuntu.com

and DNS activity associated with:

chatgpt.com
Security Significance

DNS is an important source of information during network security monitoring.

Analysts can use DNS traffic to identify:

Domains requested by hosts
External destinations
Connectivity checks
Application-related activity
Potentially suspicious domain-resolution patterns

DNS traffic should always be interpreted within its context.

The presence of a domain name in a capture does not by itself establish that the domain is malicious.

Assessment

The observed DNS activity was generated during normal laboratory activity and was not independently classified as malicious.

The finding is therefore informational.

NSM-004 — Cleartext HTTP Traffic Visibility
Description

The HTTP analysis demonstrated that application-layer HTTP information can be directly inspected within a packet capture when traffic is transmitted without TLS protection.

The HTTP capture contained request and response traffic.

Examples included:

GET / HTTP/1.1

and:

HTTP/1.1 200 OK
Security Significance

Traditional HTTP does not provide the same confidentiality protection as HTTPS.

Because HTTP application data is not protected by TLS, network observers with access to the traffic may be able to inspect protocol information and application-layer content.

This makes HTTPS/TLS preferable when confidentiality and integrity protection are required.

Assessment

The observation was intentionally generated as part of the laboratory exercise to demonstrate the difference between cleartext HTTP and encrypted HTTPS traffic.

It represents a security characteristic of the protocol rather than evidence of an attack.

NSM-005 — TLS-Protected Application Traffic
Description

The HTTPS analysis demonstrated TLS negotiation followed by protected application traffic.

The capture contained TLS protocol exchanges including:

Client Hello
Server Hello
Cryptographic negotiation
Key exchange information
Encrypted application data
Security Significance

TLS provides cryptographic protection for application traffic transmitted over HTTPS.

Unlike the HTTP capture, the application-layer content was not directly displayed as readable HTTP requests and responses.

This demonstrates the confidentiality benefit provided by TLS.

Assessment

The observed TLS traffic represents expected encrypted communication generated during the laboratory exercise.

The finding is therefore informational and demonstrates a security control rather than a vulnerability.

3. Overall Security Assessment

The network traffic analysis demonstrated several important security monitoring capabilities.

The laboratory successfully demonstrated:

Identification of network endpoints
Identification of TCP connection attempts
Observation of TCP SYN retransmissions
Identification of SSH traffic
Analysis of DNS activity
Inspection of cleartext HTTP traffic
Identification of TLS-protected traffic
Differentiation between local laboratory traffic and external network communication

The analysis also demonstrated the relationship between network monitoring and system hardening.

Project 1 established the Linux server security controls, while Project 2 provided packet-level evidence showing how the resulting network behavior can be observed and analyzed.

4. Recommended Monitoring Actions

Based on the observations from this laboratory, the following monitoring practices are recommended for a production security monitoring environment:

Monitor unexpected TCP connection attempts to sensitive services.
Investigate repeated connection attempts and unusual SYN retransmission patterns.
Monitor DNS queries for unusual domains, abnormal query volumes, and unexpected destinations.
Identify cleartext protocols where encryption is expected.
Monitor TLS connections and investigate unexpected external destinations.
Maintain an inventory of authorized network services.
Correlate packet-level observations with host-based logs and firewall records.
Preserve packet captures and supporting evidence during security investigations.


5. Limitations

The findings in this document are based on controlled laboratory traffic.

The captures do not represent the complete traffic profile of a production network.

TCP retransmissions were not treated as proof of malicious activity.

No determination of malicious intent was made solely from packet-level observations.

Additional evidence such as firewall logs, endpoint logs, authentication logs, process information, and longer-duration network captures would be required for a production security investigation.

6. Conclusion

The investigation demonstrated how Wireshark can be used as a network security monitoring and analysis tool.

The captured traffic provided visibility into TCP connections, service exposure, retransmissions, DNS activity, HTTP communication, and TLS-protected traffic.

The findings demonstrate practical skills in packet analysis, network troubleshooting, security monitoring, evidence collection, and defensive cybersecurity investigation.

The laboratory also demonstrates how network-level monitoring can complement host-level security hardening by providing visibility into the actual traffic generated by and directed toward a secured system.
